Users Reported Critical Friction

The pain was real and growing

  1. Minutes-long startup — loading 40K resources into memory at launch
  2. Destructive overwrites — no version history, last-write-wins
  3. No concurrent editing — single-user lock on the entire catalog
  4. No branching — experimental changes polluted production
  5. Excessive memory pressure — entire catalog resident in RAM

“We lost three days of work because someone overwrote the connector namespace. There was no way to recover.”

The Vision: Git-Like Version Control for JSON

We envisioned a system where every change is tracked, every branch is isolated, and every client stays in sync.

Core Principles

  • Immutable changesets — content-addressed, tamper-proof
  • Channels — isolated branches for safe experimentation
  • Distributed sync — push/pull like Git, but for JSON
  • Lazy loading — on-demand, not all-at-once

Lazy Loading: Minutes → Milliseconds

Instead of loading 40,000 resources at startup, lazy clients fetch only metadata, materialise on-demand, cache locally, and receive real-time updates.

Traditional Loading

Startup: Load ALL 40K resources
         ├── Fetch from S3        ~45s
         ├── Deserialize JSON     ~30s
         ├── Build index          ~15s
         └── Ready                ~90s total
         Memory: ~2.4 GB resident

Lazy Loading

Startup: Connect + fetch metadata
         ├── WebSocket connect    ~50ms
         ├── List resource IDs    ~200ms
         └── Ready                ~250ms total
         Memory: ~12 MB baseline

On-Demand Materialisation

  1. User requests resource by ID
  2. Client fetches patches from server
  3. Replays RFC 6902 operations
  4. Caches materialised snapshot
  5. Subsequent reads hit local cache

Cache Invalidation

  • WebSocket push on changeset commit
  • Client re-materialises affected resources
  • Delivers UpdateEvent with full metadata

Lazy Loaders in Four Languages

Identical semantics across Rust, Go, Python, and WebAssembly — connect, list, get, subscribe.

Rust (lazy-cat)

let client = LazyClient::connect(url).await?;
let ids = client.list_resources().await?;
let resource = client.get_resource(&id).await?;
client.on_update(|event| {
    println!("Updated: {:?}", event.affected_resources);
}).await;

Go (lazy-go)

client := lazydyna.NewClient(url)
client.Connect(ctx)
ids, _ := client.ListResources(ctx)
res, _ := client.GetResource(ctx, id)
client.OnUpdate(func(e UpdateEvent) {
    fmt.Printf("Updated: %v\n", e.AffectedResources)
})

Python (lazy-py)

async with LazyClient(url) as client:
    ids = await client.list_resources()
    resource = await client.get_resource(id)
    async for event in client.updates():
        print(f"Updated: {event.affected_resources}")

WASM (lazy-wasm)

const client = await LazyWasmClient.new(url);
const ids = client.list_resources();
const resource = client.get_resource(id);
client.on_update((event) => {
    console.log("Updated:", event.affected_resources);
});

Roadmap: What Comes Next

Near Term

  • Three-way merge — automatic conflict resolution for non-overlapping edits
  • Partial namespace sync — subscribe to subsets of the catalog
  • JSON Schema validation — enforce resource structure at commit time
  • Incremental materialisation — apply only new patches, skip replayed history

Long Term

  • Federated catalogs — multi-server sync across organizational boundaries
  • Conflict resolution UI — visual merge tool in the Elm app
  • Performance benchmarks — published comparisons of full vs. lazy loading
  • Branch/merge operations — Git-like workflows with channel promotion

Design Principles Going Forward

Every feature must preserve the core invariants: immutable changesets, content-addressable storage, and lazy-by-default loading.
